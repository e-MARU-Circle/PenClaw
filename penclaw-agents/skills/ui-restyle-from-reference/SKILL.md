# ui-restyle-from-reference — 「イケてる風」を仕様に変える

「UIをもっとイケてる感じに」は指示ではなく感想である。感想のまま全画面を作り直すと、完成後に丸ごと差し戻される。本スキルは、**参照デザイン → トークン表 → ギャップ表 → 1画面パイロット → 合意 → 展開**の順で、主観要求を検証可能な仕様に変換する工程を定める。

| 依頼の実態 | そのまま着手すると | 本スキルの変換先 |
|---|---|---|
| 「イケてる風にして」 | 何を直せば終わりか誰も言えない | トークン表（全項目埋め） |
| 「この参考に寄せて」 | 参考の一部だけ拾って別物になる | ギャップ表（画面×要素で未達を列挙） |
| 「デザインもUXもコードも」 | 範囲が無限に伸びる | 工程0で範囲と完了条件を先に確定 |

## 大原則

**参照は分解して使い、丸写ししない。** 抽出するのは配色・余白リズム・タイポの比率・コンポーネントの質感といった**方法**であって、他社プロダクトの画面構成やコピーそのものではない。参照元の固有要素（ロゴ・独自イラスト・特徴的なブランド表現）を再現物に持ち込まない。

**トークンは全項目を埋める。部分適用は必ず崩れる。** 自院の図版で実測した事例では、色の正本7トークンのうち背景色とアクセント色の2つだけを拾い、残りを独自値で埋める取りこぼしが4件中3件で発生した（D-057 → D-077）。同じ事故がUIでも起きる。埋められない項目は独自値を入れず「未取得」と書いて工程1へ差し戻す。

**全画面をやる前に1画面で合意を取る。** 基準が言語化されていない以上、方向性の誤りは作った量に比例して損失になる。

# 工程

## 工程0 — 範囲と完了条件の確定

着手前に `AskUserQuestion` で次を確定し、答えが出るまで実装に入らない。対象プロダクトと画面の数、今回の範囲（見た目のみか、UX導線とコードまでか）、期限、そして**誰が合格を判定するか**。判定者が依頼元の別人である場合は、パイロットをその人に当てるまでが工程4に含まれる。

参照が複数あるときは**優先順位を1本に決める**。「A の配色と B の余白」のような混成は、後で不整合の原因が特定できなくなる。主たる参照1本＋補助という形にする。

## 工程1 — 参照の読み取り

参照URLはブラウザで開いて読む（Claude in Chrome、または内蔵ブラウザ）。Refero のスタイルページは実プロダクトのUIスクリーンショットをスタイル単位で束ねたギャラリーで、1ページ＝1つの傾向を表す。**テキスト説明だけで判断せず、必ずスクリーンショットを取得して視覚で確認する。** 取得できないときは先生に画面共有かスクショ提供を依頼し、推測で先に進まない。

読み取り結果は、この時点では言葉で書かない。次の工程の表に直接入れる。

## 工程2 — トークン表に固定する

参照から次の表を**全行**埋める。値は具体値（HEX・px・倍率）で、形容詞で書かない。

| 分類 | トークン | 例 |
|---|---|---|
| 色 | bg / surface / surface-alt | 面の3階層 |
| 色 | fg / fg-muted | 前景と副次前景 |
| 色 | border | 罫線・区切り |
| 色 | accent / accent-tint | 主アクセントと淡色面 |
| 色 | danger / success | 状態色 |
| タイポ | font-display / font-body | 見出し・本文の書体 |
| タイポ | scale | 本文基準に対する見出し倍率（例 1.25） |
| タイポ | leading / tracking | 行間・字間 |
| 空間 | space-unit | 余白の最小単位（例 4px）とその倍数系列 |
| 形 | radius-sm / md / lg | 角丸3段 |
| 形 | shadow | 影の段数と強さ |
| 動き | motion | トランジション時間とイージング |

**採用の可否は色から判定する。** 本文と背景のコントラスト比が 4.5:1 を下回る組み合わせは、参照がそうであっても採用しない。参照は見栄えの根拠であって、可読性の根拠ではない。

自院（江間ファミリー歯科）の図版・院内資料が対象の場合は、外部参照ではなく `PenClaw司令室/diagram_design/style-guide-emashika.md` の7トークンが色の正本になる。本スキルの工程2は外部参照ベースの案件に限って適用する。

## 工程3 — ギャップ表

現行UIを画面単位で棚卸しし、トークンとの差分を列挙する。列は「画面 / 要素 / 現状値 / 目標トークン / 影響度 / 工数」。影響度は、**最初に目に入る面**（ファーストビュー、主要CTA、ナビゲーション）を高に置く。ここで工数が読めない行は、読めないと書く。

## 工程4 — パイロット1画面

影響度が最も高い1画面だけを、トークンを**CSS変数として定義した上で**作り直す。この時点で値を直書きしない。直書きすると展開時にトークンの変更が伝播せず、工程5が全面書き直しになる。

出来上がりを判定者に当て、合否と修正指示を受ける。**ここで合意が取れるまで工程5へ進まない。** 差し戻しが2回を超えたら、参照の選定（工程0の優先順位）に誤りがあると判断して工程0へ戻る。

## 工程5 — 展開

合意済みのトークンとパイロットのコンポーネントを他画面へ適用する。適用後、各画面で**7分類すべてが入っているか**を機械的に確認する。トークンを定義したCSS変数名で grep し、未使用の変数と直書き値の残骸を洗い出す。

## 工程6 — デックスレビュー

実装の妥当性検証はカイ・マコト単独で完結させず、デックス（Codex/Fugu）に投げてから判断する（カスタム指示の振る舞いルール8）。レビュー観点は、トークンの直書き残り、コントラスト比、レスポンシブ時の破綻、既存計測タグ（gtag・AWタグ）の巻き込み欠落の4点。

---

## 落とし穴

**計測タグを巻き込んで消す。** UIを作り直すときにCTAボタンを差し替えると、gtag・AWタグ・gclidプレフィルが一緒に消える。2026-07-17 に patient-chat widget で主CV2本が10日間ゼロになった実例がある。CTAに触れたら計測の同梱を必ず確認する。

**テーマ内JSのキャッシュ。** 江間ファミリー歯科のテーマ内JS資産は cache-control が1年。JSを直したら参照側全ファイルの `?v=` バンプが必須で、忘れると本番だけ旧版が動き続ける。

**参照サイトの読み取り失敗を「デザインが分からない」と報告しない。** 読めなかったのは参照であって要求ではない。スクショを依頼して工程1をやり直す。

**LPテンプレは自己完結型で `wp_head`/`wp_footer` を呼ばない。** emasika.jp の各LPはフック注入が効かないため、共通スタイルの差し込みは各テンプレ本体に直書きする。

## 成果物と置き場

`PenClaw司令室/ui_restyle/<案件名>/` 配下に、日付接頭辞付きで3点を残す。`YYYY-MM-DD_トークン表_<案件名>.md`、`YYYY-MM-DD_ギャップ表_<案件名>.md`、パイロットの成果物。日付は `TZ=Asia/Tokyo date "+%Y-%m-%d"` で実日を取ってから書く（ハードルール16）。

案件が一区切りしたら `arch-hub` で棚卸しし、俯瞰図に統合する。
